Claude Code · Custom Agents

Agents that remember your project and play well with others.

The third time I typed the same prompt, I wrote it down as an agent. Here's how those agents carry context, how they hand work to each other, and where that falls apart.

7 min read · Claude Code users with prompts they keep retyping

01 · The trigger

A repeated prompt is an agent waiting to be written

Most of my agents started the same way. I'd paste a long prompt for a recurring job (triage a review comment, resolve a merge conflict, review a PR), notice I was pasting it again, and finally move it into a file.

A custom agent is just a markdown file in ~/.claude/agents/ (yours everywhere) or .claude/agents/ (one repo). The frontmatter says when to use it and what it may touch. The body is the system prompt.

---
name: review-triage
description: Triages a PR review comment. Use for "is this in scope?"
  and "what do we reply?". Shows a draft first, never posts unasked.
tools: Read, Grep, Glob, Bash
model: opus
---

You are the review-triage agent. ...

The description is the part people underinvest in. Claude uses it to decide whether to delegate, so it should say when to use the agent, not only what it is.

Don't write it from scratch. After a long working session, the context is already full of what the agent needs: the architecture, the decisions, the traps you hit. I ask Claude to turn that session into an agent ("create an agent from what we learned here") and then trim the result. The first draft is built from real work, not from what I remember to write down. Open /agents to review and edit it.

My rule of thumb: third repeat becomes an agent. Second repeat is a note in CLAUDE.md. First time is just a prompt. Writing agents too early just gives you files to maintain.

02 · Context

How an agent knows your project

A fresh agent starts with an empty context. It has your code, but not your history, conventions, or the traps you've already fallen into. I give mine that knowledge in three layers, from most stable to most volatile.

L1

The agent body

Stable facts that rarely change: architecture overview, one section per component, shared conventions, hard rules, the output format.

Edit when: the architecture changes.

L2

Ground-truth files, read at the start

The agent's first instruction is "read these files before anything else": a conventions doc, a list of known traps, the current ticket. The agent stays small; the facts live in files you update anyway.

Edit when: the facts change. No agent edit needed.

L3

Session and memory context

CLAUDE.md, the project's memory directory, and whatever the current session has already loaded. This is where "we decided X yesterday" lives.

Edit when: you learn something worth keeping.

The split matters because of staleness. Facts baked into the agent body go out of date silently. So I keep L1 to things that are structural, and push anything that changes weekly into L2 files the agent re-reads on every run.

Trap: an agent prompt that says "the current branch is X" or "the open PRs are Y" is wrong the day after you write it. Have it re-verify anything it relies on, and say so in the prompt.

03 · Anatomy

The skeleton I reuse

Different agents, same shape. This is the generic version, with the sections that earned their place:

# 1. Who and how it thinks
You are the X agent. You think like a careful senior developer
who ships small, safe changes.

# 2. Context
## Ground truth (read first, every run)
- docs/conventions.md
- docs/known-traps.md

# 3. Hard rules
## No guessing
- Cite file:line for every factual claim. Unverified = "assumed".
- Re-verify anything remembered from a previous run.

# 4. Decision rubric
## Verdicts
BLOCKER | FIX NOW | DEFER | DISAGREE | ASK

# 5. Output cap
## Output
Max 4 lines per item. No essays.

# 6. Acting
## Acting
Show the draft first. Take the action only after explicit go-ahead.

# 7. Learning
## Learning
When corrected, note the rule here so it isn't repeated.

Three of these do most of the work. Hard rules carry over the habit from my previous post: cite sources, mark guesses. The output cap keeps results short enough to act on. "Show first, act on approval" is what makes it safe to give an agent write access to anything outward-facing.

04 · Cooperation

Orchestrator and specialists

One agent that knows everything gets long and vague. The pattern that worked better: an orchestrator that only classifies and delegates, and specialists that each know one domain well.

Orchestrator: fetch the diff, classify files by domain
↓ fan out, in parallel
Backend
APIs, queries, auth
Frontend
components, state
Database
schema, migrations
DevOps
CI, infra, config
↓ each returns findings only
Orchestrator: dedupe, rank, one consolidated review

Two details keep this from turning into noise. First, the orchestrator gets no domain opinions of its own; its job is routing and synthesis. Second, every specialist is told to return only findings, not narrate what it read. That keeps the orchestrator's context small enough to synthesize cleanly.

Routing is mostly the description field again. A tight description like "Use for SQL, ORM models, and migrations" is what gets the right specialist picked without you naming it.

05 · Across sessions

When the other agent is a different session

Subagents live inside one session: the parent spawns them, they report back, they're gone. But I usually have several sessions open at once, one per project. Claude Code has tools for crossing that boundary:

ToolWhat it does
ListAgentsLists agents you can message: in-process subagents, teammates, and other local Claude sessions on the machine.
SendMessageSends a message to one of them by name, and can continue a subagent you spawned earlier with its context intact.

That second use is the one I rely on most. Spawning a fresh subagent for each follow-up throws away everything it learned. Messaging the existing one keeps its context, so "now check the second file too" costs a sentence instead of a re-briefing.

For messaging other sessions, the useful mental model is a colleague, not a function call. You hand over what you know, ask a specific question, and treat the answer as input to verify, not as truth.

Know the limits: a message to another session carries only what you write in it. It does not see your conversation. If it needs context, put the context in the message.

06 · Failure modes

Where this breaks

Multi-agent setups fail in boring ways. These are the ones I hit:

FailureWhyFix
Stale contextFacts baked into the agent body drift out of date.Move changing facts to L2 files. Tell the agent to re-verify.
Wrong agent pickedVague description.Say when to use it, and when not to.
Conflicting editsTwo agents change the same file.Give specialists read-only tools. One writer per file.
Noisy synthesisSpecialists return full narration."Findings only, under N words."
Unwanted actionAgent posts or deletes without asking."Show first, act on go-ahead" in the prompt, tools trimmed.
Agent sprawlAgents written too early, never maintained.Third-repeat rule. Delete the unused.

The "conflicting edits" row is the one that bites hardest. Giving most specialists only Read, Grep, and Glob removes the problem at the source, and it makes them safer to run in parallel.

07 · Takeaways

Before you write the next agent

  • 01Wait for the third repeat, then have Claude draft the agent from the session that did the work.
  • 02Write the description for routing. When to use it, when not to.
  • 03Layer the context. Stable in the body, changing in files it re-reads, learned in memory.
  • 04Cap the output and trim the tools. Short results, minimum access.
  • 05Show first, act on approval for anything outward-facing.
  • 06Message, don't respawn, when a follow-up needs the earlier context.

An agent isn't magic. It's a prompt you stopped retyping, plus the context you got tired of re-explaining. The payoff comes from keeping it small, current, and a little bit suspicious of itself.
