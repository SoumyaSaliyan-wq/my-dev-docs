Claude Code · Lessons Learned

Confidence is not evidence:
fixing Claude Code's wrong guesses.

After months of daily use, the biggest time sink wasn't bad code. It was a wrong guess, stated calmly, that I built three fixes on top of. One loop and three habits stopped it.

6 min read · Anyone using Claude Code daily on real code

01 · The pattern

The fix that fixed nothing

Here's a composite of something that happened to me more than once, with the details changed. A service intermittently times out. I paste the error and ask for help.

Me

Requests to the orders API time out sometimes. Can you look?

Claude

The client timeout is 5 seconds, which is too low under load. I've raised it to 30.

Me

Still timing out.

Claude

Then connection pooling is exhausted. I've bumped the pool size and added retries.

Me

Worse now. Requests take 90 seconds to fail.

Reality

The client timeout was never 5 seconds. The 5 came from an old default Claude assumed. The real cause was a downstream dependency returning 503, and the new retries multiplied the load.

Nothing here is a coding mistake. Every edit was syntactically fine. The failure was the first sentence: a claim with no source, delivered with full confidence, and then treated as fact by everything after it.

02 · Why it happens

Confidence is a tone, not a measurement

Claude writes "the timeout is 5 seconds" in the same voice whether it just read that line in your config or is filling in a typical default. The prose doesn't change. You can't tell the difference by reading it.

Two things make it worse over a long session:

Its own guesses become context. Once a wrong claim is in the conversation, later turns treat it as an established fact and reason from it.

Fixes stack. Each patch changes the system, so the next symptom looks different, and the original wrong assumption is now buried under three edits.

The reframe: I stopped asking "is Claude right?" and started asking "what would show me?" Every claim should either point at evidence or be marked as a guess.

03 · The loop

One loop for every task

This is the whole system. Six steps, with one rule: if verification fails, the fix is reverted and I go back to evidence, not forward to another patch.

01
Plan
No edits. Assumptions listed.
02
Evidence
Root cause with a source.
03
Small fix
One cause, one change.
04
Verify
Reproduce, then re-run.
05
Second look
Fresh reviewer, diff only.
06
Commit
Only after 1 to 5.
verify fails → revert the fix → back to 02. never patch on top of a failed patch.

The next three sections are the habits that make steps 1, 2 and 4 work in practice. Each one is a prompt change you can start using today.

04 · Habit 1

Demand a source for every claim

If Claude states a value, a name, or a behavior, the follow-up is always the same: where did that come from? A real answer is a file and line, a log entry, or a command output. A weak answer ("it's typically...") tells you it was a guess.

Before

why is the request timing out?

Result: a confident story built from common causes. Plausible, unverified.

After

why is the request timing out? for each claim, give the file:line or log line it comes from. mark anything you couldn't verify as "assumed".

Result: sourced claims, plus an explicit list of guesses to check first.

The "assumed" label is the useful part. It turns an invisible guess into a to-do item, and it's usually where the bug is hiding.

Cheap test: when a detail seems oddly specific (a table, a flag, a config key), ask "did you read this, or infer it?" Inference is fine. Presenting inference as a reading is the problem.

05 · Habit 2

Root cause first. Revert when a fix fails.

"Still broken" is the most dangerous message to send mid-session, because the default reaction is another patch. After a failed fix, I do two things instead: revert it, and make Claude go back to evidence.

Before

still timing out, try something else

Result: new theory, new edit, on top of the old edit. Two unknowns now.

After

revert that change. read the logs and find the root cause. don't assume anything we haven't seen in the logs.

Result: back to a known state, and a cause traced to actual output.

Reverting feels like losing progress. It isn't. A failed fix is information: it tells you the theory was wrong. Keeping the edit just muddies the next experiment.

Watch for: a fix that "seems to work" without ever reproducing the original failure. If you never saw it fail, you can't know you fixed it. Reproduce first, then fix, then re-run the same reproduction.

06 · Habit 3

Plan first. No edits until I say so.

A wrong plan costs one sentence to correct. A wrong diff costs a review, a revert, and sometimes a merge conflict. So for anything non-trivial, the first prompt asks for thinking, not code.

Before

add rate limiting to the API

Result: a full implementation, picked library, chosen limits, edited five files. None of it discussed.

After

high-level plan only for adding rate limiting. don't edit anything. list your assumptions and what you'd check first.

Result: a short plan I can correct: "you assumed per-IP, we need per-user."

The "list your assumptions" line does double duty. It's the same trick as habit 1, applied before any code exists.

07 · Make it stick

Put the rules where you don't have to retype them

I kept typing the same corrections, so I moved them into my global CLAUDE.md. Claude reads it every session, so the habits apply even when I'm tired and my prompt is lazy.

# CLAUDE.md

- Start with the simplest minimal change. A small fix request gets a small fix.
- Confirm your understanding before editing. If ambiguous, ask.
- Cite file:line or log output for factual claims. Label guesses "assumed".
- If a fix fails, revert it before trying another approach.
- "Test locally" means mock external dependencies. Leave no test artifacts
  in real systems.

For step 5 of the loop, I use a second reviewer. The key detail: give it the diff, not your conclusion. If you hand over "I think the bug is X, confirm," it tends to confirm. If you hand over the change and ask "what could this break?", it looks.

Pairs well with: a built-in advisor or review subagent for step 5. A fresh context hasn't absorbed the earlier wrong guesses, which is exactly why it catches them.

08 · Takeaways

The five-line version

  • 01Plan before code. Ask for assumptions, approve, then edit.
  • 02Every claim gets a source. Unsourced means "assumed", and assumptions get checked first.
  • 03One cause, one small fix. Resist bundling "while we're here" changes.
  • 04Reproduce, fix, re-run. If the fix fails, revert, don't stack.
  • 05Fresh eyes on the diff before commit, with no conclusion attached.

None of this is about distrusting the tool. Claude Code is fast and often right, and these habits make the "often" safer. The goal is to catch the wrong guess at step one, when it costs a sentence, instead of at step six, when it costs an afternoon.
